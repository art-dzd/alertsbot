# Контракт POST /notify

`X-Alerts-Token: <ALERTS_TOKEN>`. Авторизация всегда до чтения/разбора тела.
Неверный, отсутствующий токен или пустой настроенный секрет: `401`, WARNING,
без строки истории и отправки.

Вход — JSON-объект. Рекомендуемые поля:

```json
{"service":"billing","title":"Ошибка обработки","message":"Задача упала","details":"trace_id=abc","event_id":"incident-123"}
```

`service`, `title`, `message`: пропущенные/null заменяются `[поле <имя> отсутствует]`,
пустые — `[поле <имя> пустое]`. Нестроковые значения сериализуются в JSON-строку.
`details`, `event_id` необязательны; null/отсутствие — без значения, пустая строка
становится отсутствием с WARNING. Неизвестные поля игнорируются.

Любой JSON-объект проходит в доставку. Для Telegram service обрезается до 128,
title до 256, message до 4096, details до 8192 символов; полный текст хранится в БД.
Длинный event_id принимается целиком: SHA-256 полного значения используется в кэше,
в журнале длинный идентификатор отображается хэшем. Одинаковые начала разных
идентификаторов не объединяются. Нормализация/обрезка при успешной доставке даёт
`notify_done` WARNING `outcome=fallback` с именами полей и причинами, без их содержимого.

Невалидный JSON, массив, строка, число, null: `422 {"detail":"Expected JSON object"}`,
WARNING `invalid_json_object`, история `rejected` без содержимого запроса.

## Формат Telegram

Три строки: service, title, message. При наличии details — пустая строка и details.
Итоговый текст ограничен 4096 символами с маркером
`[сообщение усечено до лимита Telegram]`. parse_mode отсутствует.
Отправка синхронно внутри HTTP-запроса; SQLite commit делается до неё.

## Ответы

| Код | Тело | Причина |
|---|---|---|
| 200 | `{"status":"sent"}` | Доставлено или прежний успех из кэша |
| 401 | `{"detail":"Unauthorized"}` | Нет авторизации |
| 422 | `{"detail":"Expected JSON object"}` | Тело не JSON-объект |
| 422 | `{"detail":"Telegram payload rejected"}` | Telegram 400 |
| 424 | `{"detail":"Permanent Telegram error"}` | Другие постоянные 4xx Telegram |
| 502 | `{"detail":"Temporary Telegram error"}` | Сеть, 5xx или исчерпанный 429 |

Ответ содержит `X-Request-ID`. Ошибка SQLite не меняет код/тело ответа доставки.

## История и повторы

Каждый авторизованный запрос создаёт строку, включая rejected и повторы из кэша.
До доставки статус `pending`, после — `sent`/`failed`, HTTP- и Telegram-статусы,
безопасная причина, UTC-время успешной отправки. Кэшированный повтор отмечается
`cached=1`, время отправки берётся из первоначального результата.

event_id: TTL один час, до 10 000 записей в памяти одного воркера. Кэшируются успех
и постоянные ошибки (`422` Telegram/`424`). `502` не кэшируется: клиент повторяет
тот же event_id и получает реальную попытку. Без event_id каждый запрос отправляется.
Параллельные запросы одного события не создают дубль. Рестарт сбрасывает кэш.

История хранится 5 лет, чистится при старте и на запросах не чаще раза в час.
Это история попыток, не очередь: нет автоматического восстановления доставки
после остановки процесса. `pending` требует проверки; при отказе БД запись может
отсутствовать, но отправка продолжается и ошибка видна в ERROR.
